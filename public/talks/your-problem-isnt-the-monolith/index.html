Six years of monolith. Eighteen months of microservices.

Same engineers. Same data. Different outcome.

I've seen versions of this story at multiple orgs over the last two years. Spring Boot monolith. Six years. Tests fast, deploys fine. People felt slow, so they migrated to microservices. Eighteen months in: deploys slower, on-call incidents tripled, two senior engineers quit. Postmortem: the shape of the system wasn't the problem. Every service they extracted still needed to read tables in services they hadn't extracted yet. They built a microservices distribution on top of a shared database, and they called it progress. Same engineers. Same data. Different outcome. The variable that changed wasn't talent or architectural fashion. It was something else. That's this talk.

Architecture endures when teams align on data lifecycles, not just APIs.

This is the talk. We are going to walk through one company. They got the modular monolith right. Then they decomposed without trauma. The thing they did was not a deployment trick. It was data discipline.

Aggregates own their invariants.

DIAGRAM: Order aggregate root

Inside boundary: OrderLine, ShippingAddress, Money
Outside boundary (referenced as IDs only): CustomerId, ProductId
An aggregate is the only place an invariant lives. If an Order can't ship without a confirmed payment, that rule lives in Order. Not in a service layer. Not in a database trigger. Not in a Slack message. In Order. The aggregate is the transactional boundary because it's the only thing that knows the rules.

What this looks like in practice

WRONG


// Tax module mutating Order's data directly
orderRepository.findById(id).getLines()
    .forEach(line -> line.setTaxRate(rate));

RIGHT


// Tax sends a command. Order owns the transition.
orderService.applyTaxes(orderId, taxBreakdown);

// inside Order aggregate:
//   validates state, applies rule, emits event
If your tax module is reaching into Order's tables, you don't have an Order aggregate. You have a database with Java in front of it. Twenty seconds on the right side: write logic encapsulated, validation at the boundary, emits an event.

Other teams consume contracts, not tables.

DIAGRAM: Tax needs Order data

Tax subscribes to OrderPlaced and OrderShipped events.
Tax builds its own local read projection.
Tax never queries Order's tables.
Tax does not join to Order's tables. Tax subscribes to events Order publishes. From those events, Tax builds its own projection: order lines, prices, shipping address, the fields Tax cares about. The contract is the event. Order can refactor its schema tomorrow. Tax doesn't notice, because Tax was never reading the schema.

The contract is the boundary.


OrderPlaced:
  version: 3
  fields:
    orderId: UUID
    customerId: UUID
    placedAt: timestamp
    lines: [OrderLine]
    shippingAddress: Address
    currency: ISO4217
This is the only thing Tax knows about Order. Versioned, owned by Order's team, published with a guarantee. Order's internal tables are nobody else's business.

Discipline is not a wiki page.
It's CI exit code 1.

I have seen every one of these patterns documented in Confluence and broken in production the same week. The only way they hold is if a CI build fails when they break. So here is the slide most architecture talks don't show.

Fitness functions for data boundaries.


@AnalyzeClasses(packages = "com.penultimate")
public class DataBoundaryFitnessFunctions {

  @ArchTest
  static final ArchRule no_cross_domain_persistence_access =
    noClasses().that().resideInAPackage("..tax..")
      .should().accessClassesThat()
      .resideInAPackage("..orders.persistence..")
      .because("Tax reads OrderPlaced events. Tax does not query Order's tables.");

  @ArchTest
  static final ArchRule writes_only_via_aggregate_root =
    noClasses().that().resideOutsideOfPackage("..orders.domain..")
      .should().callMethod(OrderRepository.class, "save", Order.class)
      .because("Order's invariants live in Order. No exceptions.");

  @ArchTest
  static final ArchRule events_versioned_and_immutable =
    classes().that().areAnnotatedWith(DomainEvent.class)
      .should().haveSimpleNameEndingWith("V1")
      .orShould().haveSimpleNameEndingWith("V2")
      .andShould().haveOnlyFinalFields();
}
Three rules. Each one took an afternoon to write. Each one runs on every PR. The first one stops Tax from reaching into Order's database. The second stops anyone outside Order from saving an Order. The third makes sure events are versioned and immutable. This is the slide you should photograph. (Pause for cameras.)

Other fitness functions you'll add

  • Schema migration linter (expand/contract enforcement)
  • Contract stability test (Pact, schema-registry compatibility)
  • Cross-aggregate join detector (SQL log analysis or query plan inspection)
  • Event schema validation (in CI, against registry)
  • Lifecycle/retention assertions (per-table TTL declared, enforced)
These don't fit on one slide. They all live in CI. Build them gradually. Each one buys you back a category of bug you used to find in production.

Aggregates become extraction boundaries.

Search subscribes to ProductPublished, OrderPlaced.

When Search was extracted, almost nothing in Search's code changed. It already consumed events. It already had its own projection of catalog data. The boundary was already there. The extraction was a deployment change, not a redesign.

Same contract. Bigger blast radius.

DIAGRAM: Read model contract — side by side

Year 4: consumed by 1 internal team.
Year 7: consumed by 6 internal teams + 2 external integrations.

The Tax read model existed before extraction. After extraction it has a name, a version, an SLA, and consumers it didn't have before. That's the work of decomposition: making implicit contracts explicit, and giving them an owner.

Process managers replace transactions.

DIAGRAM: Order placement, before and after

Year 4: single DB transaction across Order, Payment, Tax, Inventory.
Year 7: process manager — PlaceOrder → AuthorizePayment → ApplyTaxes → ReserveInventory.
Each step has compensation.
The order placement that used to be a five-table transaction is now a process manager with compensation. Choreography for the simple paths, orchestration for the multi-step flows. The point isn't to avoid transactions. The point is to know when you have one and when you have a saga, and to never confuse the two.

Duplication owned by a contract is not debt.
It's autonomy.

Tax keeps its own copy of order line items. Search keeps its own denormalized catalog projection. Both update from events; both own their schema.

Stop apologizing for duplication. Tax has its own copy of the parts of an order it cares about. Search has its own copy of catalog data, denormalized for query performance. Both copies are owned. Both update from events. That is autonomy. The opposite of duplication isn't elegance. It's coupling.

The discipline is portable.


// Year 4 rule:
// "Tax doesn't access Order's persistence package."

// Year 7 rule:
@ArchTest
static final ArchRule tax_only_consumes_versioned_order_events =
    classes().that().resideInAPackage("..tax.consumer..")
      .should().onlyDependOnClassesThat()
      .areAnnotatedWith(VersionedDomainEvent.class)
      .because("Tax consumes events. Tax does not call Order's APIs.");
When you decompose, your CI gets stronger, not weaker. The schema-boundary rule becomes a service-boundary rule. The contract-stability rule becomes a published-event rule. Same discipline, new transport.

Decomposition wasn't a flag day. It was four moves over three years.
Each one obvious, because the seams were already drawn in the data.

That's it. No big rewrite. No transformation program. Three extractions, four moves, in the order the data lifecycle asked for them.
