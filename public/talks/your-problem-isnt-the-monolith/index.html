01·Ownership

Aggregates own their invariants.

DIAGRAM: Order aggregate root

Inside boundary: OrderLine, ShippingAddress, Money
Outside boundary (referenced as IDs only): CustomerId, ProductId
An aggregate is the only place an invariant lives. If an Order can't ship without a confirmed payment, that rule lives in Order. Not in a service layer. Not in a database trigger. Not in a Slack message. In Order. The aggregate is the transactional boundary because it's the only thing that knows the rules. In code, the difference shows up every time another team needs Order's data.

02·Contracts

Other teams consume contracts, not tables.

This is how Tax gets Order's data. [CLICK] Two teams. Order on the left, owns its data. Tax on the right, needs some of it. [CLICK] The lazy answer is for Tax to query Order's tables directly. That couples them forever — any schema change in Order breaks Tax. [CLICK] The right answer is the one Penultimate took. Order publishes events. Tax subscribes. Tax builds its own projection of the fields it cares about. The contract is the event, not the schema. Order can refactor tomorrow. Tax doesn't notice. The event is small. The schema behind it isn't. Let me show you both, side by side.

Discipline is not a wiki page.

03·CI fitness

Fitness functions for data boundaries.


@AnalyzeClasses(packages = "com.penultimate")
public class DataBoundaryFitnessFunctions {

  @ArchTest
  static final ArchRule no_cross_domain_persistence_access =
    noClasses().that().resideInAPackage("..tax..")
      .should().accessClassesThat()
      .resideInAPackage("..orders.persistence..")
      .because("Tax reads OrderPlaced events. Tax does not query Order's tables.");

  @ArchTest
  static final ArchRule writes_only_via_aggregate_root =
    noClasses().that().resideOutsideOfPackage("..orders.domain..")
      .should().callMethod(OrderRepository.class, "save", Order.class)
      .because("Order's invariants live in Order. No exceptions.");

  @ArchTest
  static final ArchRule events_versioned_and_immutable =
    classes().that().areAnnotatedWith(DomainEvent.class)
      .should().haveSimpleNameEndingWith("V1")
      .orShould().haveSimpleNameEndingWith("V2")
      .andShould().haveOnlyFinalFields();
}

Three rules. One CI build. The four failure modes — blocked at the door.

Three rules. Each one took an afternoon to write. Each one runs on every PR. The first one stops Tax from reaching into Order's database. The second stops anyone outside Order from saving an Order. The third makes sure events are versioned and immutable. This is the slide you should photograph. (Pause for cameras.) Three rules for one team. A fuller suite ends up looking like this.

04·Safe migrations

Migrations expand. Then contract.

Every step is reversible. None of them is a flag day.

01 Expand

Add the new column nullable. Dual-write from the app.

Drop the column. Old reads were never touched.

02 Backfill

Populate new column from old. Idempotent, restartable.

Re-run. Or pause and resume; the script is a fact, not a flag.

03 Switch reads

Reads move to the new column behind a feature flag.

Flip the flag back. Both columns still hold the truth.

04 Contract

Stop writing the old column. Drop it in a later deploy.

Only safe once no reader has touched old for a full retention window.

Enforced in CI: an Expand without its Contract is a failed build.

The Monday-morning migration is the one that takes the site down. Not because the migration is wrong — because it tried to do everything at once. Expand-then-contract turns one risky deploy into four boring ones. Add the new column nullable. Backfill in the background. Switch reads behind a flag. Then, weeks later, drop the old column once the metrics say no one is reading it. Every step has a one-line rollback that doesn't lose data. And here's the trick that makes it stick — the fitness function from the previous slide watches for this. An Expand without a matching Contract eventually fails the build. The discipline isn't "write good migrations." The discipline is: the build won't let you forget to finish one. Five disciplines, four covered. The fifth is the one the audience asked about back at slide 2 — when do we finally split this thing? Here's when. And why it cost Penultimate nothing dramatic.

05·Decompose along seams

Process managers replace transactions.

DIAGRAM: Order placement, before and after

Year 4: single DB transaction across Order, Payment, Tax, Inventory.
Year 7: process manager — PlaceOrder → AuthorizePayment → ApplyTaxes → ReserveInventory.
Each step has compensation.
The order placement that used to be a five-table transaction is now a process manager with compensation. Choreography for the simple paths, orchestration for the multi-step flows. The point isn't to avoid transactions. The point is to know when you have one and when you have a saga, and to never confuse the two. Process managers handle multi-step writes. What about the reads each team now keeps?

05·Decompose along seams

Duplication owned by a contract is not debt.
It's autonomy.

Tax keeps its own copy of order line items. Search keeps its own denormalized catalog projection. Both update from events; both own their schema.

Stop apologizing for duplication. Tax has its own copy of the parts of an order it cares about. Search has its own copy of catalog data, denormalized for query performance. Both copies are owned. Both update from events. That is autonomy. The opposite of duplication isn't elegance. It's coupling. If duplication is the rule, CI has to keep enforcing the same boundaries — just across the network.

When you decompose, your CI gets stronger, not weaker. The schema-boundary rule becomes a service-boundary rule. The contract-stability rule becomes a published-event rule. Same discipline, new transport.
