1

Data Contracts & Quality

Agents Can't Smell Bad Data

This is Topic 1. We're starting with the most foundational layer: data quality and contracts. The core insight: humans have a "smell test" for bad data. They notice when a number looks off, when a date doesn't make sense, when a price seems wrong. Agents don't have that instinct. They treat every value as truth and act on it immediately. When the data is wrong, agents don't hesitate — they confidently produce wrong outcomes. Without trusted data, nothing else in agentic AI works.

Humans have a smell test. They notice when data feels stale, when numbers look off, when something doesn't add up.

Agents have no smell test. They act on stale data with the same confidence as fresh data.

Every step was "correct." The data was the problem.

Let me give you a concrete scenario. A pricing agent is asked for the current price of Product X. Yesterday, the price was updated from $49.99 to $59.99. But the agent's data source hasn't been refreshed — it still shows the old price. The agent doesn't hesitate. It retrieves $49.99, quotes the customer, the customer buys, and the company loses $10 per unit. Every step the agent took was technically correct — it followed its workflow perfectly. The data was the problem. A human sales rep would notice: "Wait, didn't we update this last week?" They'd double-check. They have institutional memory and a smell test. The agent has neither. This is the fundamental challenge: agents treat every value as truth. Errors don't trigger warnings — they cascade silently through the workflow. In a Precisely / Drexel LeBow survey of 565-plus data professionals, only 12% of organizations reported their data was of sufficient quality and accessibility for AI at all — and that bar was set before anyone was handing data to autonomous agents. The real agent-readiness number is almost certainly lower.

Schema is law: Data contracts as code

kind: DataContract

name: Product Pricing
version: 1.0.0
status: active

  - name: product_pricing
    physicalType: TABLE
    properties:
      - name: product_id

        logicalType: timestamp
        required: true

So how do we prevent that? The answer is data contracts — treating schema as law, not a suggestion. This reverses the "schemaless is flexible" trend. For human consumers, loose schemas are inconvenient. For agents, they're dangerous. The YAML on the left is a data contract in Data Contract Specification format — the same format used by Data Contract CLI, which Thoughtworks Radar Volume 33 highlighted. Let's walk through it: the product_pricing schema defines properties with strict logical types, a quality rule that price must be greater than zero, a quality check on currency that rejects any value outside USD, EUR, or GBP, and critically — a freshness SLA that price data must be less than 24 hours old. On the right, three enforcement dimensions: schema enforcement ensures types and constraints are respected; freshness SLAs define max staleness per dataset — nightly batch updates are insufficient when agents answer in real-time; quality gates validate contracts in CI/CD and block deployments on failure. This is the pricing scenario from the previous slide prevented by design. If the price data is older than 24 hours, the contract is violated before the agent ever sees it.

So we've defined the contract — but what happens when data violates it? You need a circuit breaker. That's the quarantine pattern. Let's walk through the flow: raw data arrives from source systems — APIs, databases, streams. Before it enters the agent-accessible data store, it passes through a contract validation gate. The gate checks three things: does it match the schema, is it within the freshness SLA, and does it pass quality rules? If it passes all three — it enters the Gold tier, agent-ready data. If it fails any check — it's quarantined. Sent to a dead letter queue for human review, with alerts fired. The critical insight: the agent never sees the bad data. It doesn't get poisoned by stale prices or corrupt embeddings. If the pricing data from our scenario hits the quarantine gate and the updated_at timestamp is older than 24 hours, the contract is violated — the data is quarantined. The agent, when asked about the price, says "I don't have current pricing data" instead of confidently quoting the wrong price. That's dramatically better. This is a data architecture pattern, not a model-level fix. You can't prompt-engineer your way out of bad data.

Now that we have a way to quarantine bad data, where does the good data go? That's where the medallion architecture comes in. Microsoft's Cloud Adoption Framework defines this for data platforms. The first three tiers are well-established: Bronze is raw, immutable ingestion — you keep everything for audit trail and lineage. Silver is validated and deduplicated — schema is applied, data contracts are enforced, this is where the quarantine pattern sits. Gold is certified — the semantic layer from Topic 3 is applied here, access is governed, metrics are trusted. The fourth tier — Adaptive Gold — is the novel addition for agentic architectures. This is where agents become active participants in data curation, not just consumers. They monitor their own query patterns, identify frequently accessed data combinations, and materialize optimized datasets. Think of it as agents building their own data warehouse views based on actual usage patterns. The key architectural principle: agents should only access Gold tier or above. Bronze and Silver exist for lineage, debugging, and human investigation. Exposing raw or partially-validated data to agents is asking for the pricing problem we just talked about.

So we have contracts, quarantine, and a medallion architecture. But what about the grey area — when data isn't clearly bad, but isn't fully trustworthy either? That's where confidence-threshold routing comes in. It's the bridge between full autonomy and full human control. Let's walk through the left side: the agent processes a request and assesses data quality signals — not just model confidence, but data-level signals like freshness, completeness, and consistency. If confidence is at or above 85%, the agent proceeds autonomously. If it's below 85%, it defers to a human for review. The threshold number is configurable per use case — pricing might be 90%, internal FAQs might be 70%. On the right, we revisit the pricing scenario. The price data is 3 days stale. The freshness SLA says 24 hours. The SLA is violated, which automatically lowers the confidence score below the threshold — regardless of how confident the model itself feels about the answer. The agent responds: "I'm not confident this price is current. Routing to a human for verification." This is dramatically better than the outcome from our earlier scenario where the agent quoted the wrong price. The key architectural insight: data quality signals should drive confidence thresholds, not just model-level confidence. A model can be very confident about a stale answer. The freshness SLA violation overrides that model confidence.

2

Traceability & Governance

Auditing Autonomous Agents

In Topic 1 we established that data needs to be trusted — contracts, quality gates, quarantine patterns. But even with perfect data, when agents act autonomously, who's watching? How do you audit what happened? How do you answer a regulator who asks "why did the agent do this?" That's what this topic addresses. The shift from "what happened" to "why it happened" is the fundamental challenge of agentic governance.

The audit gap

Trade finance scenario

Agent processes letter of credit: checks customer KYC, verifies compliance rules, approves $2.4M transaction — all in 30 seconds.

6 months later…

A regulator asks: "Why was this approved?"

Can you answer with full reasoning chains? Or just timestamps and table names?

Traditional audit

"What" happened — which tables were accessed, timestamps, user IDs

Agentic audit

"Why" — which sources did the agent consult, what reasoning chain led to the decision, what alternatives were considered and rejected

The gap between these two is where regulatory risk lives.

Let's look at a real-world example that shows why this matters. DBS Bank built their agentic AI for trade finance, and governance architecture was the key innovation. Imagine: an agent processes a letter of credit — it checks KYC data, verifies the customer isn't on a sanctions list, evaluates credit terms, and approves a $2.4 million transaction. All in 30 seconds. Six months later, a regulator asks: "Why was this approved?" Traditional audit logs can answer "what happened" — which database tables were queried, at what time, by which service account. But they can't answer "why" — why did the agent decide to check the sanctions list before the credit terms? Why did it approve despite a minor discrepancy in the documentation? What alternatives did it consider? The gap between "what" and "why" is where regulatory risk lives. The EU AI Act's Article 12 requires high-risk systems to keep automatic logs precisely so this kind of "why" can be answered after the fact.

And this isn't theoretical — there are real regulatory teeth behind it. The EU AI Act is the most specific regulation on the books. Article 12 requires high-risk AI systems to automatically log events over their lifetime so their operation can be traced, and Article 19 requires providers to keep those logs for at least 6 months. Breaching these record-keeping obligations sits in the Act's middle penalty tier — up to 15 million euros or 3% of global annual turnover, whichever is higher. The headline 35-million / 7% figure you sometimes see is real, but it's for a different tier — the outright prohibited AI practices — not record-keeping. Even so, 3% of a major bank's global turnover runs into the hundreds of millions. In practice this means three things: first, automatically log events, enough to reconstruct not just "what happened" but "why"; second, retain those logs for at least 6 months, which means your observability infrastructure needs to handle long-term storage; third, be able to explain the "why" — which data sources were consulted, what logic was applied, what alternatives were considered and rejected. This isn't just an EU issue. The US has the NIST AI Risk Management Framework. The UK has its AI Safety Institute. Singapore has its Model AI Governance Framework. The direction is clear globally: if you deploy autonomous AI systems, you will need to explain what they did and why.

Each stage requires

• More trust — proven reliability at the previous level

• More observability — increasing monitoring scope

• More governance — stronger audit trails and controls

So the regulations are clear — you need audit trails and reasoning chains. But how do you actually roll this out? You don't deploy an agent with full autonomy on day one — just like you don't give a new employee unrestricted access. Stage 1: Shadow mode — the agent recommends actions but doesn't execute them. A human makes the final decision. The agent's recommendations are fully logged, so you can track accuracy over time. This is the lowest-risk starting point. Stage 2: Supervised — the agent prepares the action but waits for human approval before executing. The human reviews and clicks "approve" or "reject." Full audit trail of both the agent's proposal and the human's decision. Stage 3: Autonomous with guardrails — the agent acts within defined boundaries. Transactions under $10K might be auto-approved, but anything above triggers a human review. Alerts fire on exceptions. Stage 4: Full autonomy — the agent acts independently with continuous monitoring and periodic spot-check audits. This is earned — you get here only after the agent has proven reliable at each previous stage. The analogy resonates with any manager: you wouldn't give a new hire the corporate credit card on day one. They start with purchase requests, graduate to supervised spending, then eventually earn a card with limits. Agents should follow the same trust-building path.

As agents earn more autonomy through those stages, the question becomes: what permissions should they actually have? Two critical security patterns address this. First: delegated access. When Alice asks the agent to check her account, the agent should act with Alice's permissions — not a broad service account that can see all customer data. If the agent uses a shared service account, you lose attribution. When the regulator asks "who accessed this customer's data?", the answer is "the service account" — which tells you nothing. With delegated access, the answer is "Alice's agent, acting on Alice's behalf, with Alice's permissions." Second: just-in-time credentials. Instead of giving the agent a persistent API key that never expires, you issue a short-lived token for each specific task. The agent needs to check the sanctions list? Issue a token that grants OFAC API read access, scoped to the specific customer, valid for 5 minutes. When the task completes, the token expires. No persistent credentials sitting around waiting to be compromised. Third: least privilege. The agent gets the minimum access needed for the specific task. Processing a letter of credit doesn't need access to HR systems or marketing data. These three patterns together solve the attribution and scope problems that plague most current agentic deployments.

Semantic Layers

Teaching Agents What Your Data Means

In Topics 1 and 2 we established the foundation — trusted data and governance. Now we add the context layer: when AI agents become the primary consumers of your data, they need explicit context that human analysts carry implicitly. A semantic layer provides that context.

Your agent doesn't know what "revenue" means

The agent receives:

"What was Q3 revenue for Product X?"

It doesn't know:

→ Which table to query

→ Gross sales or net of returns?

→ What "Q3" maps to in your fiscal calendar

→ Which joins connect products → orders → revenue

Your analyst knows all of this

Two years of institutional knowledge, absorbed through osmosis, tribal docs, and Slack threads.


Your agent has none of it.

So what does this lack of context actually look like? Imagine an agent gets asked "What was Q3 revenue for Product X?" A human analyst knows exactly what to do — which table to query, whether revenue means gross or net, what Q3 maps to in your fiscal calendar. They've absorbed all of that through two years of institutional knowledge, tribal docs, and Slack threads. The agent has none of it. It doesn't know which joins connect products to orders to revenue. It doesn't know your fiscal calendar starts in February. Without that context, it either hallucinates an answer or gives up. This is the gap a semantic layer fills.

So how do we give the agent that context? Through a semantic layer. And a semantic layer is a set of declarative definitions — typically YAML — that encodes three things: how metrics are calculated, how entities relate to each other, and what the business rules are. The critical property: these are defined as code in Git, go through pull requests, get tested in CI, and progress through test environments before reaching production. When the definition of "revenue" changes, you change one YAML file and it propagates everywhere. The architecture diagram on the right shows where it sits: between the raw data and the consumers. Agents never touch the raw layer directly — they go through the semantic layer, which constrains and governs their access.

Metrics as code


semantic_models:
  - name: orders
    entities:
      - name: order_id
        type: primary
      - name: customer_id
        type: foreign
    measures:
      - name: revenue
        agg: sum
        expr: order_amount - discount_amount
    dimensions:
      - name: order_date
        type: time
        type_params:
          time_granularity: day

Agent asks:

"What was Q3 revenue for Product X?"

▼ semantic layer resolves to

SELECT SUM(order_amount - discount_amount)
  FROM orders o
  JOIN products p ON o.product_id = p.id
 WHERE p.name = 'Product X'
   AND o.order_date
       BETWEEN '2025-07-01'
           AND '2025-09-30'

So how do agents actually connect to all these data sources and tools across the three tiers? That's where MCP comes in. MCP — Model Context Protocol — is the emerging standard for connecting AI models to data sources and tools. The USB-C analogy works well: before USB-C, every device had its own connector. You needed N times M custom integrations — every model paired with every tool. MCP reduces this to N plus M — each model speaks MCP, each tool speaks MCP, and they all interoperate. The numbers are real: by early 2026 the official MCP SDKs were seeing roughly 97 million downloads a month — up from about 2 million a month at launch — with thousands of community- and vendor-built servers in the ecosystem. And in December 2025 the protocol moved to the Agentic AI Foundation, hosted by the Linux Foundation and co-founded by Anthropic, Block, and OpenAI, putting it under open, vendor-neutral governance. Every major AI provider has adopted it — Anthropic, OpenAI, AWS, Google, Microsoft. This isn't proprietary — it's an industry standard. Thoughtworks Radar Volume 33 highlighted MCP as a dominant theme across multiple blips. Worth mentioning: Google's A2A — Agent-to-Agent protocol — is a complementary standard focused on agent-to-agent communication rather than agent-to-tool. It's still early days for A2A though — adoption isn't nearly as ubiquitous as MCP, so we're focusing on MCP today as the more mature and widely supported protocol.

Now that we know what MCP is, let's look at how it works. MCP has three primitives — and understanding them is critical for your data architecture decisions. Resources are read-only — they expose data for agents to discover and consume. Think of them as the agent equivalent of a GET endpoint. Prompts are reusable templates that shape how agents approach tasks — like an IT triage workflow that guides the agent through diagnostic steps. Tools are functions agents can invoke — they have real-world side effects like creating tickets, updating records, or triggering workflows. The risk escalates left to right: Resources are safe (read-only), Prompts shape behavior (they influence agent decisions), and Tools have real-world consequences (they change state). This maps directly to Microsoft's framing: RAG corresponds to Resources, MCP-Read adds structured real-time access, MCP-Write corresponds to Tools. For our PO payment scenario: Resources provide the troubleshooting docs, the Prompt guides the triage workflow, and Tools execute check_po_payment_status() and create_ticket().

Now here's a critical warning. This is one of the most common mistakes we see. Organizations take their existing REST APIs and do a 1-to-1 wrapping as MCP tools — every endpoint becomes a tool. The result is tool sprawl. On the left, we have 50 tools with names like get_po_payment_status, create_ticket_po_payment, create_ticket_po_payment_network. The agent has to choose from 50 tools with minimal context — and LLMs are demonstrably bad at this. Accuracy drops significantly as tool count increases. Thoughtworks Radar Volume 33 placed "naive API-to-MCP conversion" on HOLD — meaning don't do this. On the right, the same functionality is exposed as 3 well-designed capabilities with rich descriptions and parameterized inputs. check_service_status takes a service name and location — one tool handles all services and all locations. create_support_ticket is parameterized with category, priority, and description. The descriptions are detailed enough for the LLM to understand when to use each tool. The principle: design capabilities, not endpoints. 5-10 well-described business capabilities will outperform 50 thin API wrappers every time.

MCP = vertical (agent ↔ tools)   |   A2A = horizontal (agent ↔ agents)

So we've talked about MCP connecting agents to tools. But what about agents talking to each other? That's where A2A comes in. The key insight for data architects: there are two protocols emerging as standards. MCP is vertical — it connects agents to tools and data sources below them. A2A — Agent-to-Agent Protocol — is horizontal — it connects agents to each other for multi-agent collaboration. In our PO payment scenario, the IT Support Agent might delegate to a PO Ops Agent (via A2A) to run deeper diagnostics, while each agent connects to its own tools and data via MCP. Google announced A2A with 150+ supporting organizations. The data architecture lesson: your data and APIs need to be designed for machine consumers regardless of which protocol carries the traffic. The properties that make data agent-ready — rich descriptions, parameterized access, clear schemas — are universal.

So here's how it all fits together. The four topics we covered form a layered architecture — and the order matters. At the bottom: the Data Foundation. Contracts, quality gates, medallion architecture, freshness SLAs. This is what makes your data Trusted. Without it, nothing above works. Layer 2: the Semantic Context Layer. Layer 3: the Agent Access Layer. MCP, function-calling APIs, A2A, capability-oriented tools. This is what makes your data Operational. This is what makes your data Traceable and Governed. You can't have meaningful observability without governed access to observe. Each layer depends on the one below it. Skip a layer, and the layers above collapse. This is why so many agentic AI projects fail — they jump straight to the agent access layer without building the foundation underneath.

So if you remember four things from this session. First: Context over models. The semantic layer is the highest-ROI investment you can make. The AtScale benchmark showed less than 20% to over 95% accuracy — same model, different context. Second: Read before write. Start with MCP Resources — read-only access.
