RAG can search documents — it retrieves the right troubleshooting guide.

But it can't query live systems to check if VPN is actually down in Chicago right now.

And it can't take action — no ticket creation, no status update, no workflow trigger.

Agentic AI needs data that's not just searchable — it's actionable.

Set up the core problem with a concrete scenario everyone can relate to. An employee reports a VPN issue. An ideal AI agent would do three things: retrieve the relevant troubleshooting guide, check if the VPN service is actually down right now, and create a helpdesk ticket if needed. Traditional RAG — the pattern most organizations have deployed — can only do step 1. It can search documents and retrieve relevant content. But it can't query a live monitoring system to check service status, and it certainly can't create a ticket in ServiceNow or Jira. This gap — between searchable and actionable — is what this topic addresses. We'll use this VPN scenario as a running example throughout.

Introduce the three-tier data access spectrum. This framing comes from Microsoft's Cloud Adoption Framework for AI, which formalizes it as RAG plus MCP-Read plus MCP-Write. Tier 1 is where most organizations are today — retrieval-augmented generation, vector search, document lookup. The agent can find relevant content. Tier 2 adds real-time structured access — the agent can query live systems, check service status, read from databases in real-time. Tier 3 is the most powerful and the most dangerous — write-back. The agent can create tickets, update records, trigger workflows. Each tier adds capability but also adds risk. The VPN scenario maps cleanly: retrieve the guide (Tier 1), check VPN status (Tier 2), create the ticket (Tier 3). Most organizations have only deployed Tier 1. The shift to agentic AI requires all three — and that's what the rest of this topic addresses.

MCP — Model Context Protocol — is the emerging standard for connecting AI models to data sources and tools. The USB-C analogy works well: before USB-C, every device had its own connector. You needed N times M custom integrations — every model paired with every tool. MCP reduces this to N plus M — each model speaks MCP, each tool speaks MCP, and they all interoperate. The numbers are real: over 97 million SDK downloads, more than 10,000 community-built MCP servers, and in December 2025 Anthropic donated the protocol to the Linux Foundation for open governance. Every major AI provider has adopted it — Anthropic, OpenAI, AWS, Google, Microsoft. This isn't proprietary — it's an industry standard. ThoughtWorks Radar Volume 33 highlighted MCP as a dominant theme across multiple blips.

Risk escalates left to right: safe → shapes behavior → real-world consequences

MCP has three primitives — and understanding them is critical for data architecture decisions. Resources are read-only — they expose data for agents to discover and consume. Think of them as the agent equivalent of a GET endpoint. Prompts are reusable templates that shape how agents approach tasks — like an IT triage workflow that guides the agent through diagnostic steps. Tools are functions agents can invoke — they have real-world side effects like creating tickets, updating records, or triggering workflows. The risk escalates left to right: Resources are safe (read-only), Prompts shape behavior (they influence agent decisions), and Tools have real-world consequences (they change state). This maps directly to Microsoft's framing: RAG corresponds to Resources, MCP-Read adds structured real-time access, MCP-Write corresponds to Tools. For our VPN scenario: Resources provide the troubleshooting docs, the Prompt guides the triage workflow, and Tools execute check_vpn_status() and create_ticket().

@tool

    category: str, priority: str
) -> Ticket: ...

3 tools → clear agent decisions
Rich descriptions · Parameterized · Composable

LLMs are bad at choosing from large tool sets. 5-10 well-described capabilities beat 50 thin wrappers.

This is one of the most common mistakes we see. Organizations take their existing REST APIs and do a 1-to-1 wrapping as MCP tools — every endpoint becomes a tool. The result is tool sprawl. On the left, we have 50 tools with names like get_vpn_status_chicago, get_vpn_status_nyc, create_ticket_vpn, create_ticket_network. The agent has to choose from 50 tools with minimal context — and LLMs are demonstrably bad at this. Accuracy drops significantly as tool count increases. ThoughtWorks Radar Volume 33 placed "naive API-to-MCP conversion" on HOLD — meaning don't do this. On the right, the same functionality is exposed as 3 well-designed capabilities with rich descriptions and parameterized inputs. check_service_status takes a service name and location — one tool handles all services and all locations. create_support_ticket is parameterized with category, priority, and description. The descriptions are detailed enough for the LLM to understand when to use each tool. The principle: design capabilities, not endpoints. 5-10 well-described business capabilities will outperform 50 thin API wrappers every time.

"Build with any framework. Equip with MCP. Communicate with A2A."

— Google, Agent-to-Agent Protocol announcement · 150+ supporting organizations

MCP = vertical (agent ↔ tools)   |   A2A = horizontal (agent ↔ agents)

Brief positioning slide — don't go deep here, the Red Hat session covers MCP protocol mechanics in detail. The key insight for data architects: there are two protocols emerging as standards. MCP is vertical — it connects agents to tools and data sources below them. A2A (Agent-to-Agent Protocol) is horizontal — it connects agents to each other for multi-agent collaboration. In our VPN scenario, the IT Support Agent might delegate to a Network Ops Agent (via A2A) to run deeper diagnostics, while each agent connects to its own tools and data via MCP. Google announced A2A with 150+ supporting organizations. The data architecture lesson: your data and APIs need to be designed for machine consumers regardless of which protocol carries the traffic. The properties that make data agent-ready — rich descriptions, parameterized access, clear schemas — are universal.

This is the payoff slide — everything from slides 2 through 7 comes together. Walk through it left to right. Step 1, RETRIEVE: the agent uses RAG to look up the VPN troubleshooting guide for the Chicago office. This is a Resource — read-only, safe. Step 2, QUERY: the agent calls check_vpn_status() — a Tool that reads live system data. It discovers the Chicago VPN gateway has been down since 08:47, affecting 23 users. This is real-time structured access — Tier 2. Step 3, ACT: the agent calls create_ticket() — a Tool that writes. It creates a high-priority ticket, auto-routes it to NetOps, and links all 23 affected users. This is write-back — Tier 3. The dashed return path shows the agent's coherent response to the employee — combining all three tiers into one natural answer. The whole process takes about 30 seconds. Manually, the employee would wait in a queue, explain the issue, the support agent would check the monitoring dashboard, create the ticket — 15 minutes minimum. Three data tiers, two MCP primitives (Resources and Tools), one coherent action.

Three numbers that frame where the industry is. First: 97 million MCP SDK downloads — the protocol adoption is real and accelerating. The technology side of the equation is largely solved. Second: only 52% of organizations can track and audit what agents are doing with their data — from the Salesforce State of Data and Analytics report. That means nearly half have no visibility. Third: Gartner predicts more than 40% of agentic AI projects will fail by 2028 — not because the models aren't capable, but because the organizational infrastructure isn't ready. The technology to make agents act exists. What's missing is the data governance, quality, and traceability infrastructure to make them act safely. That's the bridge to our next two topics: Data Contracts and Quality (Topic 3) and Traceability and Governance (Topic 4). Actionable data requires actionable governance.

What you can do Monday morning

1

Map your data access tiers

Pick your top 3 agent use cases. For each, classify what's needed: read-only retrieval, real-time structured access, or write-back actions. Most gaps are in Tiers 2 and 3.

2

Design capabilities, not endpoints

Group your APIs into 5-10 business capabilities with rich descriptions. Think "what can this agent do?" not "what endpoints exist?"

3

Start with MCP Resources

Read-only first — lowest risk, immediate value. Expose knowledge bases and configuration data. Graduate to Tools only after governance is in place.

4

Instrument from day one

Log every tool invocation: who triggered it, what was called, when, and on behalf of whom. You'll need this for audit and debugging.
