This is Topic 1 of our session "Making Data AI-Ready for Agentic AI." We're starting with the most foundational shift: when AI agents become the primary consumers of your data, they need explicit context that human analysts carry implicitly. A semantic layer provides that context.

Change "revenue" once → propagates everywhere

Define this concretely for the technical audience. A semantic layer is a set of declarative definitions — typically YAML — that encodes three things: how metrics are calculated, how entities relate to each other, and what the business rules are. The critical property: these are defined as code in Git, go through pull requests, get tested in CI. When the definition of "revenue" changes, you change one YAML file and it propagates everywhere. The architecture diagram on the right shows where it sits: between the raw data and the consumers. Agents never touch the raw layer directly — they go through the semantic layer, which constrains and governs their access.

Metrics as code


semantic_models:
  - name: orders
    entities:
      - name: order_id
        type: primary
      - name: customer_id
        type: foreign
    measures:
      - name: revenue
        agg: sum
        expr: order_amount - discount_amount
    dimensions:
      - name: order_date
        type: time
        type_params:
          time_granularity: day

Agent asks:

"What was Q3 revenue for Product X?"

▼ semantic layer resolves to

SELECT SUM(order_amount - discount_amount)
  FROM orders o
  JOIN products p ON o.product_id = p.id
 WHERE p.name = 'Product X'
   AND o.order_date
       BETWEEN '2025-07-01'
           AND '2025-09-30'

dbt MetricFlow — similar patterns in Cube.js, Snowflake Semantic Views, Databricks Metric Views

Walk through the YAML on the left. Point out that the business logic — revenue equals order_amount minus discount_amount — lives right here in the semantic layer, not buried in a BI tool or SQL view. Then show the right side: the agent receives a natural language question, and the semantic layer resolves it to correct, constrained SQL. The agent doesn't guess table names or join paths — it uses the definition. This is dbt MetricFlow syntax, but Cube.js, Snowflake, and Databricks all follow similar patterns. The tool matters less than the discipline of getting this into version-controlled code.

Same question, very different SQL

"What was Q3 revenue for Product X?"

Without semantic layer


-- Agent guesses table names
SELECT SUM(amount)
  FROM sales_data
 WHERE product = 'Product X'
   AND quarter = 'Q3'

Wrong table · Uses gross amount not net · No fiscal calendar mapping · Missing join to products

With semantic layer


-- Constrained by metric definition
SELECT SUM(order_amount
         - discount_amount)
  FROM orders o
  JOIN products p
    ON o.product_id = p.id
 WHERE p.name = 'Product X'
   AND o.order_date
       BETWEEN '2025-07-01'
           AND '2025-09-30'

Correct table · Net revenue formula · Fiscal Q3 resolved · Valid join path

This is the same question from slide 2 — now we see the actual SQL difference. On the left, the agent without a semantic layer guesses at table names, uses the wrong column, has no fiscal calendar mapping, and misses the join. On the right, the semantic layer constrains the agent to the correct table, the net revenue formula from the YAML definition, the fiscal calendar dates, and the valid join path. The audience can see this isn't a subtle difference — it's the difference between a wrong answer and a right one.

The semantic layer constrains the LLM — only valid dimensions appear for selected metrics. That's a feature, not a bug.

Walk through the pipeline left to right. The agent sends a natural language question (step 1). The semantic layer (center, green glow) is the star: it looks up metric definitions, valid dimensions, join paths, and access rules via MCP (step 2), then generates constrained SQL (step 3) — both happen inside the same component. The data warehouse executes the query (step 4). The result flows back to the agent with full lineage metadata (step 5, dashed return path). The critical architectural insight: the semantic layer CONSTRAINS what the agent can ask for. dbt's semantic layer dynamically shows only the dimensions applicable to selected metrics. This prevents the agent from generating plausible-sounding but incorrect queries. Step 5 is the foundation for traceability in Topic 4.

What you can do Monday morning

1

Audit your tribal knowledge

Identify your top 10-15 business metrics. Document how they're actually calculated today. You'll find 2-3 conflicting definitions for the important ones.

2

Define metrics as code

Pick a tool that fits your stack:
dbt → MetricFlow Standalone → Cube.js
Snowflake → Semantic Views

3

Expose it to your agents

Connect via MCP server or API. The agent queries the semantic layer, never the raw schema.

4

Test with adversarial questions

Ask ambiguous terms, edge cases, cross-domain joins. Every hallucination = a gap in your semantic definitions.

Anti-pattern: Don't boil the ocean — start with the metrics your first use case needs, not a full warehouse model.

This is the take-it-home slide. Make it concrete. Step 1: Most organizations have conflicting definitions for their most important metrics. Revenue is the classic — gross vs. net, with or without returns. Find these conflicts. That's your biggest agent risk and quick win. Step 2: The tool matters less than the discipline. If you're already using dbt, MetricFlow is natural. If you need standalone, Cube.js is excellent. Snowflake and Databricks native features are maturing fast. Step 3: dbt, Cube, and AtScale all have MCP servers. The agent should never touch your raw schema. Step 4: Best way to find gaps is adversarial testing. Every hallucination points to a missing definition. Fix the definition, not the prompt. Anti-pattern: Don't boil the ocean. Start with the metrics your first agent use case needs.
