Data Contracts & Quality

Agents Can't Smell Bad Data



Pramod Sadalage & Premanand Chandrasekaran · ThoughtWorks

This is Topic 3. In Topics 1 and 2 we covered the semantic layer — teaching agents what your data means — and actionable data access — giving agents the ability to read, query, and write. The teaser from Topic 2 was: agents can act, but can they trust your data? That's what this topic addresses. The core insight: humans have a "smell test" for bad data. They notice when a number looks off, when a date doesn't make sense, when a price seems wrong. Agents don't have that instinct. They treat every value as truth and act on it immediately. When the data is wrong, agents don't hesitate — they confidently produce wrong outcomes.

Humans have a smell test. They notice when data feels stale, when numbers look off, when something doesn't add up.

Agents have no smell test. They act on stale data with the same confidence as fresh data.

Every step was "correct." The data was the problem.

Set up the core problem with a concrete scenario. A pricing agent is asked for the current price of Product X. Yesterday, the price was updated from $49.99 to $59.99. But the agent's data source hasn't been refreshed — it still shows the old price. The agent doesn't hesitate. It retrieves $49.99, quotes the customer, the customer buys, and the company loses $10 per unit. Every step the agent took was technically correct — it followed its workflow perfectly. The data was the problem. A human sales rep would notice: "Wait, didn't we update this last week?" They'd double-check. They have institutional memory and a smell test. The agent has neither. This is the fundamental challenge: agents treat every value as truth. Errors don't trigger warnings — they cascade silently through the workflow. Schema is law: Data contracts as code


dataContractSpecification: 0.9.3
id: product-pricing
info:
  title: Product Pricing Contract
  owner: pricing-team
models:
  product_pricing:
    fields:
      product_id:
        type: string
        required: true
        primaryKey: true
      price:
        type: decimal
        required: true
        quality:
          - type: custom
            expression: "price > 0"
      currency:
        type: string
        required: true
        enum: [USD, EUR, GBP]
      updated_at:
        type: timestamp
        required: true
servicelevels:
  freshness:
    threshold: "24h"   # Must be < 24h for agents
{}

This slide reverses the "schemaless is flexible" trend. For human consumers, loose schemas are inconvenient. For agents, they're dangerous. The YAML on the left is a data contract in Data Contract Specification format — the same format used by Data Contract CLI, which ThoughtWorks Radar Volume 33 highlighted. Walk through it: the product_pricing model defines fields with strict types, a quality rule that price must be greater than zero, an enum constraint on currency, and critically — a freshness SLA that price data must be less than 24 hours old. On the right, three enforcement dimensions: schema enforcement ensures types and constraints are respected; freshness SLAs define max staleness per dataset — nightly batch updates are insufficient when agents answer in real-time; quality gates validate contracts in CI/CD and block deployments on failure. This is the pricing scenario from slide 2 prevented by design. If the price data is older than 24 hours, the contract is violated before the agent ever sees it.

Better for an agent to say "I don't know" than to act on bad data.

The agent gets silence instead of poison. That's a feature, not a bug.

The quarantine pattern is a circuit breaker adapted for AI data pipelines. Walk through the flow: raw data arrives from source systems — APIs, databases, streams. Before it enters the agent-accessible data store, it passes through a contract validation gate. The gate checks three things: does it match the schema, is it within the freshness SLA, and does it pass quality rules? If it passes all three — it enters the Gold tier, agent-ready data. If it fails any check — it's quarantined. Sent to a dead letter queue for human review, with alerts fired. The critical insight: the agent never sees the bad data. It doesn't get poisoned by stale prices or corrupt embeddings. If the pricing data from our scenario hits the quarantine gate and the updated_at timestamp is older than 24 hours, the contract is violated — the data is quarantined. The agent, when asked about the price, says "I don't have current pricing data" instead of confidently quoting the wrong price. That's dramatically better. This is a data architecture pattern, not a model-level fix. You can't prompt-engineer your way out of bad data.

Key principle

Agents should only access Gold or above. Bronze and Silver exist for lineage and debugging — never for agent consumption.

Microsoft's Cloud Adoption Framework defines the medallion architecture for data platforms. The first three tiers are well-established: Bronze is raw, immutable ingestion — you keep everything for audit trail and lineage. Silver is validated and deduplicated — schema is applied, data contracts are enforced, this is where the quarantine pattern sits. Gold is certified — the semantic layer from Topic 1 is applied here, access is governed, metrics are trusted. The fourth tier — Adaptive Gold — is the novel addition for agentic architectures. This is where agents become active participants in data curation, not just consumers. They monitor their own query patterns, identify frequently accessed data combinations, and materialize optimized datasets. Think of it as agents building their own data warehouse views based on actual usage patterns. The key architectural principle: agents should only access Gold tier or above. Bronze and Silver exist for lineage, debugging, and human investigation. Exposing raw or partially-validated data to agents is asking for the pricing scenario from slide 2.

Not every decision needs a human. Not every decision should skip one.

Confidence-threshold routing is the bridge between full autonomy and full human control. Walk through the left side: the agent processes a request and assesses data quality signals — not just model confidence, but data-level signals like freshness, completeness, and consistency. If confidence is at or above 85%, the agent proceeds autonomously. If it's below 85%, it defers to a human for review. The threshold number is configurable per use case — pricing might be 90%, internal FAQs might be 70%. On the right, we revisit the pricing scenario. The price data is 3 days stale. The freshness SLA says 24 hours. The SLA is violated, which automatically lowers the confidence score below the threshold — regardless of how confident the model itself feels about the answer. The agent responds: "I'm not confident this price is current. Routing to a human for verification." This is dramatically better than the slide 2 outcome where the agent quoted the wrong price. The key architectural insight: data quality signals should drive confidence thresholds, not just model-level confidence. A model can be very confident about a stale answer. The freshness SLA violation overrides that model confidence.

What you can do Monday morning

1

Define freshness SLAs

For every dataset agents touch, specify max staleness. Nightly batch ≠ real-time agent. A pricing dataset that's fine at 24h for dashboards may need <1h for a quoting agent.

2

Implement quarantine gates

Validate before ingestion. Dead letter queue for violations. Never feed bad data to agents. Start with your highest-risk datasets.

3

Start with Data Contract CLI

Define contracts as code. Validate in CI/CD. Block deployments on contract violations. Version your contracts alongside your schemas.

4

Add confidence routing

When data quality signals are low, defer to human review instead of autonomous action. Start with a high threshold (90%) and adjust down as trust builds.
